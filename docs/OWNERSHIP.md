# 分工

- **A**：框架（空壳）+ 做题、批改、反馈全链路
- **B**：其余模块的细节和打磨

## 一、整体结构：3 个应用 + 共享约定

| 应用 | 用户 | 设备 | 说明 |
|---|---|---|---|
| `apps/staff` 员工端 | 教师、经理 | 桌面为主 | 经理视图 = 教师视图 + 签字、Policy 审批等额外页面 |
| `apps/student` 学生端 | 学生 | 手机为主 | 单独部署，学生永远拿不到员工端的代码和数据接口 |
| `backend` 后端 API | 两个前端共用 | — | 唯一能访问 Google Sheets / Drive / Classroom / Claude / 企业微信的地方 |
| `packages/contract` 契约 | 三者共用 | — | API 规范、共享类型、mock 数据 |
| `packages/ui` 共享组件 | 两个前端共用 | — | 设计 token、基础组件、两端都要用的组件 |

```
apps/staff/          员工端前端
apps/student/        学生端前端
backend/             后端 API
packages/contract/   openapi.yaml、共享类型、mock 数据集
packages/ui/         样式 token、通用组件、热力图、日历、错题列表
docs/
```

## 二、第 0 步：两人一起定契约（分头开工前，约半天）

只要契约定下来，两人就能各自对着 mock 开发，互不等待。产出全部提交到 `packages/contract/`：

| 产出 | 内容 |
|---|---|
| 领域类型 | 按 domain model 定义所有类和字段 |
| API 规范 | 每个模块的接口路径、请求、返回、错误格式（`openapi.yaml`） |
| Mock 数据集 | 按 Exhibit 1–3 结构的完整假数据，两人共用同一份 |
| 前端页面接口 | 每个页面都是一个模块，导出 `render(el, params, ctx)`；`ctx` 里有 `api`、`user`、`toast` |
| 后端模块接口 | 每个后端模块导出 `register(app, deps)`；`deps` 里有 `repo`、`derive`、`policy`、`ai`、`notify`、`audit` |
| 设计 token | 颜色、字号、间距，以及组件清单和归属 |

**契约改动规则**：契约由 A 维护。任何一方要改，都提 PR，由另一方 review 后才能合并。

## 四、怎么做到互不依赖
1. **前端**：B 的页面按 `render(el, params, ctx)` 写，开发时用一个本地的临时页面加载自己的模块，`ctx.api` 先指向 mock 数据。A 的外壳做好后，只要在路由表里注册一行就能挂进去。
2. **后端**：B 的模块按 `register(app, deps)` 写，开发时传入 mock 版的 `deps`。A 的 repository、derive、ai、notify 做好后，换成真实实现即可，B 的代码不用改。
3. **数据**：两人用同一份 mock 数据集。需要新字段或新的事实表时，先改契约。
4. **目录不重叠**：每人只改自己负责的文件夹。共享的 `packages/contract` 和 `packages/ui` 按上表归属，谁负责谁改，另一方提 PR。

## 五、组装检查点
"最后一次性组装"风险太高，建议中间至少联调一次：

| 检查点 | 时机 | 内容 |
|---|---|---|
| 联调 1 | A 的外壳和后端骨架完成后 | B 挑一个页面和一个后端模块挂进去，验证契约行得通 |
| 联调 2 | 两边核心功能完成后 | 全部模块挂上，跑一遍完整 demo 流程 |
| 最终 | Demo 前 | 切换到真实 Google Sheets，冻结功能，只修 bug |

## 六、协作规则
- `main` 分支受保护，只能通过 PR 合并
- 分支命名：`a/<功能>`、`b/<功能>`
- 改动 `packages/contract` 必须由对方 review
- 每个 milestone 结束打 tag
