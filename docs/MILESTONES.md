# Milestones

M0–M2 搭框架，M3 起按功能重要性排序。每个 milestone 结束时都必须能跑起来、能演示。
负责人和接口约定见 [OWNERSHIP.md](OWNERSHIP.md)。A = 框架 + 做题批改反馈；B = 其余模块。

工程约定（所有 milestone 通用）：
1. 只写事实表；Exhibit 1–3、MasteryRecords、MistakeEntries、日报计数都是推导视图，不手改。
2. AI 输出一律先写进 AISuggestions（`pending`），只有老师的确认操作能把它变成事实。
3. 规则阈值从 Policy 读取，不写死在代码里。
4. Sheets / Drive 读写只放在 repository 层。
5. 每个外部依赖（Sheets、Drive、Classroom、企业微信、Claude）都有 mock 实现，用一个环境变量切换。

## 框架阶段

### M0 · 工程基线
**负责人**：A
**目标**：团队任何人 clone 下来，一条命令就能跑起来。
- 单仓库结构：`apps/staff/`（现有 dashboard 迁入）、`apps/student/`、`backend/`、`packages/contract/`、`packages/ui/`、`docs/`（见 OWNERSHIP.md）
- 定后端语言（建议 Node/TypeScript，可直接复用 `store.js` 的推导逻辑；Python FastAPI 也可）
- 配置管理：`.env.example`，密钥不进仓库
- Lint、format、单元测试框架；GitHub Actions 跑 lint 和测试
- 后端提供 `/health` 接口，前端能调通

**验收**：`dev` 命令同时启动前后端；CI 通过；README 写清楚运行步骤。

### M1 · 数据层和领域模型
**负责人**：A（B 评审 schema）
**目标**：领域模型落到代码和 Google Sheets 里。
- 按领域模型定义类型：Student、Module、KnowledgePoint、Test、Question、Attempt、Submission、QuestionResult、AISuggestion、Policy 等
- Sheets schema：每个事实表一个 tab，写成文档（列名、类型、主键）
- Repository 接口两套实现：内存 mock、Google Sheets（service account）
- Seed 脚本：把 mock 数据写进一个测试用 spreadsheet
- 审计日志：谁、什么时候、改了什么
- Policy 从表里读取，带版本号和 proposed / approved 状态

**验收**：同一组 API（读学生、读试卷）在 mock 和 Sheets 两种模式下结果一致；repository 有单元测试。

### M2 · 推导引擎、API 和 Portal 外壳
**负责人**：A。**这是交接点**：M2 结束后 B 的模块全部基于它开发。
**目标**：前端不再读本地 mock，而是读后端 API；三个角色的页面外壳到位。
- 推导引擎移到后端：Exhibit 1–3、掌握度、错题、日报计数、重点跟进提名
- 推导结果写回 Sheets 的 Exhibit 视图 tab
- 前端改成调用 API
- 角色：demo 阶段用角色切换器（明确标注是 mock），预留 Google 登录接口；学生只能看自己的数据
- 教师、经理、学生三套导航外壳；B 负责的页面先放占位页
- AI 服务基础封装：结构化输出调用 + 写入 AISuggestion + mock 模式（M4 批改基于它）
- 内部通知适配器接口（企业微信 Webhook）+ mock 实现

**验收**：刷新页面后数据不丢；规则边界都有测试（空白答案、多考点题的 W、重新批改不重复计数、证据不足）。

## 功能阶段

### M3 · 批改台 + 三表同步（核心功能）
**负责人**：A
**目标**：brief 第 8 步的痛点被完整解决，这是 demo 的主线。
- 待批改队列、异常队列；手动上传 PDF 或图片作为提交
- 逐题确认 DONE / W / C / 空白 + 得分，写入 QuestionResults（同一 Attempt 覆盖，不追加）
- 重新提交 ≠ 新的一次考试：attempt 号由老师确认
- 确认后同步更新 Sheets 里的 Exhibit 1–3
- 热力图下钻看证据；老师覆盖时必须填理由，并记入审计日志
- 按题批改模式（同一道题连续批所有学生）

**验收**：在界面上批改一份卷子，打开 Google Sheets 能看到三张表都已更新。

### M4 · 扫描处理 + AI 辅助批改
**负责人**：A
**目标**：把 AI 加进批改流程，同时证明它可靠。
- 答题纸模板：固定答题框 + 二维码（学生 ID、试卷 ID、页码）
- 上传后读二维码、裁剪答题框、检查清晰度；不合格进异常队列
- 扫描件存到 Drive
- AI 分两步：先转写（不给参考答案），再和参考答案比对 → 匹配 / 不匹配 / 无法判断，写成 AISuggestion
- 只发裁剪后的答题框，不发姓名
- Batch 模式（夜间预跑）和 mock 模式
- **准确率实测**：20–30 页手写样卷，统计"错判成对"比例、"无法判断"比例和整体建议正确率；比较不同模型的准确率和成本

**验收**：样卷跑完有一份准确率报告；AI 失败或无法判断时流程照样能走完。

### M5 · 学生 Portal 核心 + 错题库
**负责人**：A
**目标**：学生端闭环，让批改结果回到学生手里。
- 学生上传试卷（本地先检查二维码和清晰度）
- 我的进度：热力图、成绩、第几次考
- 错题库：W 和 C 分栏；学生提交订正，老师标记完成
- 未订正的错题进入老师的学生简报

**验收**：学生上传 → 老师批改 → 学生在错题库看到结果，全程走通。

沟通继续直接用微信／企业微信，系统不做消息粘贴、分类和回复草稿。调课审批已在 M8 Timetable 实现，
中文输入的场景由 Timetable 的中文申请理由覆盖。

### M7 · 日报 + 经理签字
**负责人**：B
**目标**：阶段 5 自动化，并且是最容易量化省时的部分。
- 事实自动计数，答疑数据需老师确认才计入
- 规则提名重点跟进学生 → 老师勾选并备注
- 经理签字后标记"已签"
- 导出或复制日报文本

**验收**：日报里的每个数字都能追溯到具体记录。

### M8 · Timetable（2026-10-13 改为只含课程，负责人改为 A）
**负责人**：A
- 员工端课表白板：按教室分栏、签到、直接调课、加课、撤销变更
- 学生端：本周课程，申请请假、改线上、改时间；老师批准或拒绝
- 批准后生成给任课老师的通知文本（复制到企业微信，不自动发送）
- 签到计数供日报使用
- 答疑预约已删除；日报的答疑人数和题数统计另定

### M9 · 增强功能（按剩余时间取舍）
**负责人**：A 做 9C 考试复盘和加练；其余 B
- 学生简报里的 AI 当天计划建议
- 考试数据记录和复盘建议（9C）；根据错题考点起草加练
- 家长周报草稿
- 学习提示（老师按次开启，考试模式锁定）
- 经理端：Policy 审批、AI 质量面板（AI 和老师判定的一致率）
- Google 登录替换角色切换器；从 Classroom 自动拉取提交

### M10 · Demo 打磨
**负责人**：A + B
- 准备完整的 demo 数据和脚本：一位老师的一个下午
- 影响测算：以 14:00–19:00 班次为基准，每个环节省多少时间，测算依据要写清楚
- 风险和 fallback 清单（接口权限、AI 出错、网络）
- 部署一个评委可以打开的版本
- 准备路演材料和答辩问题
